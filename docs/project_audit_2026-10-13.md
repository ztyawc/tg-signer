# tg-signer 项目审计（2026-10-13）

## 结论

审计基于 `main` 分支的 `b14f841`。发现 6 项应优先修复的缺陷，以及
10 项涉及调度、配置、安全边界、自动化与测试的中优先问题。
当前最有价值的改进是让任务执行、结果记录和调度时间保持一致。

前述章节记录初次审计时的状态；后续修复进度见文末。审计验证在隔离的临时目录进行。

## 验证情况与范围

- Ruff 检查通过，45 个 Python 文件格式检查通过。
- 现有测试：151 项通过（Python 3.12）；`pip check` 通过。
- 另外运行了 15 组本地探针，覆盖调度、失败记录、配置读取、客户端启动、
  消息分发、规则并发、定时阻塞、发送者过滤、迁移回滚、状态写入、配置校验、
  路径越界、数据库连接关闭、HTTP 错误状态和 startup 启动顺序。
- 探针使用模拟时钟、合成消息和临时 SQLite；消息分发使用本地安装的
  Kurigram Dispatcher。Telegram 客户端与更新解析由替身提供，HTTP 使用
  MockTransport。验证未调用真实 Telegram、OpenAI 或通知服务。
- 本地依赖：Kurigram 2.2.26、NiceGUI 3.18.0、Pydantic 2.14.1、
  croniter 6.2.4、pytest 9.1.1。版本信息描述本地环境。
- WebUI、Telegram 和 LLM 调用代码已接入项目。WebUI 运行需要 `[gui]`
  依赖；真实 Telegram 执行需要可用账号会话；LLM 执行需要环境变量或工作目录
  中的 OpenAI 配置。此次审计对这些外部服务的验证限于本地模拟。
- WebUI 当前管理签到和监控配置、账号缓存、记录与日志；自动化规则编辑和
  任务进程控制尚未接入 WebUI。

## 优先修复

### A01 / P1：迁移删除旧 JSON 早于数据库提交，失败时可能丢记录

**位置：** `tg_signer/sign_record_store.py:296`、`:317`、`:320`。

`migrate_all_json_records(remove_files=True)` 在处理每个文件时删除 JSON，
最后才提交整批数据库事务。后续文件导入失败会回滚已经插入的记录，
此前删除的 JSON 无法通过回滚恢复。

**复现：** 第一份记录正常，第二份记录的时间戳是 JSON 对象。
第二份触发 SQLite `ProgrammingError` 后，第一份 JSON 已被删除，
数据库中第一份记录也为空。

**建议：** 先验证全部记录，完成数据库提交，再清理已确认迁移的源文件。
清理失败应保留数据库中的成功迁移，并提供可重试的清理结果。
补充“后续文件失败”和“提交失败”的回归测试。

### A02 / P1：签到报错或动作超时后仍被记录为已执行

**位置：** `tg_signer/core.py:1175`、`:1183`、`:1110`、`:1475`。

单个聊天抛出 `RPCError` 后执行循环继续，最终无条件写入当天记录。
按钮等动作等待超时返回 `None`，成功路径也返回 `None`，调用方无法区分；
随后仍打印“处理完成”。超时路径还未释放 waiter。

**复现：** 唯一聊天模拟 RPC 失败，SQLite 仍出现当天记录。
按钮动作无响应时返回 `None`，未抛异常，waiter 仍处于等待状态。

**影响：** 看记录无法判断签到是否完成；再次启动可能因当天记录而跳过任务。

**建议：** 动作返回明确结果或抛出专用超时异常，在 `finally` 清理等待状态。
增加任务、聊天、动作的执行结果，区别成功、失败和部分完成。
自动重试应限定在失败步骤，避免重复发送已经成功的消息。
保留现有 SQLite 记录与旧 JSON 的兼容读取。

### A03 / P1：发送者白名单会放行身份未知的消息

**位置：** `tg_signer/automation/engine.py:433`、`tg_signer/config.py:449`。

自动化和监控的发送者过滤在 `message.from_user` 为空时直接返回 `True`，
即使明确配置了 `from_user_ids`。频道身份和匿名身份发送的消息可能走到这一分支。

**复现：** 白名单仅包含合成用户 `1001`，`from_user=None` 的消息在两套过滤器中
均返回 `True`。

**建议：** 配置白名单时，未知发送者默认不匹配。若需要支持频道身份，
显式增加 `sender_chat` 匹配规则；未配置白名单的规则保持现有兼容行为。

### A04 / P1：客户端启动失败后引用计数错误，重试不再启动客户端

**位置：** `tg_signer/core.py:247`。

进入上下文时先增加引用计数。如果 `start()` 抛出非 `ConnectionError` 异常，
引用计数没有撤销；下一次进入会认为已有使用者，直接跳过启动。

**复现：** 首次启动抛出异常后引用数为 1；再次进入后引用数为 2，
`start()` 调用次数仍为 1。

**建议：** 启动失败或启动被取消时恢复计数和初始化状态。
只在确认客户端已正常启动时接受“已连接”的状态，补充共享客户端重试测试。

### A05 / P1：共享账号的多个任务可能收不到应属于自己的消息

**位置：** `tg_signer/core.py:1201`、`tg_signer/automation/engine.py:188`。

同一账号共用客户端，消息回调都使用默认 group 0。
Kurigram 同一组对一次更新通常只调用第一个匹配的处理器。
签到过滤器只按聊天筛选，进入回调后才区分话题；第一个任务即使忽略该消息，
后面的任务也可能收不到它。自动化的 `filters.all` 存在相同分发问题。

**复现：** 同一聊天中两个任务分别等待话题 10 和 20。
用真实 Dispatcher 分发合成的话题 20 回复，只调用话题 10 的处理器，
话题 20 的任务没有收到消息。

签到循环还会在每轮注册新的回调，缺少移除操作。

**建议：** 建立按账号、聊天和话题分发的统一路由，或使用互不冲突的处理组。
回调只注册一次，并在任务结束时移除。回归测试应经过 Dispatcher，
覆盖同账号多任务、同聊天多话题、签到与自动化共存。

### A06 / P1：自动化 startup 规则可能先于客户端就绪执行

**位置：** `tg_signer/automation/engine.py:191`、`:199`。

程序先创建 startup 任务，随后才进入客户端上下文。客户端启动包含异步等待，
startup 任务可能在客户端初始化完成前调用发送 API。handler 的错误被捕获后
结束规则，连接就绪后也不会重新执行这条 startup 规则。

**复现：** 模拟客户端异步连接，真实 `UserAutomation.run()` 创建的 startup
规则在客户端未就绪时调用发送，触发“未初始化”异常；客户端之后正常就绪，
但没有再次尝试 startup。

**建议：** 在客户端确认就绪后启动 startup 和 timer 任务，统一监督其生命周期。
仅对尚未成功提交的动作重试，避免重复执行启动动作。

## 调度、配置与可靠性

### A07 / P2：计划时间与实际唤醒时间存在额外偏差，首次启动绕过延迟

**位置：** `tg_signer/core.py:1209`、`:1213`、`:1223`、`:1228`。

`now` 在执行签到前获取；执行结束后仍使用 `next_run - now` 作为等待时长，
因此本轮执行和连接关闭的耗时会额外加到实际唤醒时间上。
首次启动且当天没有记录时，会先执行签到，随机延迟只用于后续调度。

**复现：** 模拟两分钟的任务，日志计划时间为次日 `06:41:01`，
等待结束实际变为 `06:43:01`。同一探针设置三小时随机上限，首次执行仍立即开始。

**建议：** 以等待开始时的当前时间计算剩余时长，处理长任务跨过计划时间的情况。
明确提供“按计划启动”和“立即补执行”模式，保持 `run-once` 的立即执行语义。
持久化本轮计划时间与抽取的随机偏移，重启时恢复计划。

**对延迟问题的说明：** 之前看到的下一次运行时间属于日志计划值，
不能当作精确的实际触发时间；还需计入这里确认的等待偏差和实际连接耗时。

### A08 / P2：WebUI 保存配置不等于运行进程已采用配置

**位置：** `tg_signer/core.py:1161`、`tg_signer/webui/views.py:353`。

签到运行只在进入循环前加载配置。WebUI 更新磁盘文件后，
已运行进程保留旧配置，界面仅提示保存成功。

**复现：** 两轮运行间将配置中的随机上限从 10800 改为 600，
配置加载次数仍是一次，两轮抽取的上限仍为 10800。

**建议：** 立即区分“已保存”和“已生效”。增加配置版本与进程当前采用版本，
支持在安全时点重载、重新计算计划并更新聊天回调。
自动化重载优先在 automation 子系统实现；WebUI 通过明确接口展示结果。

### A09 / P2：配置校验允许会导致任务崩溃或频繁触发的值

**位置：** `tg_signer/config.py:363`、`:570`。

签到时间仅校验为字符串；随机秒数、间隔没有范围约束。
定时触发器也未要求有效 cron 或正数间隔。

**复现：** 无效 cron、`random_seconds=-1`、`sign_interval=-10` 可通过签到模型；
自动化 `interval_seconds=-60` 也可通过，计算的下次时间位于过去。
负数随机上限会在抽取时抛出异常；过去的定时时间可能使规则每轮轮询都触发。

**建议：** 保存时验证 cron、时间格式、非负随机值、正数 timer 间隔和有效动作。
规定 timer 的 cron 与 interval 选择规则。
约束增加后同时验证 V1/V2/V3 迁移链，避免旧配置转换绕过新规则。

### A10 / P2：并发执行同一规则会覆盖持久化变量

**位置：** `tg_signer/automation/engine.py:479`。

每次事件分别复制规则变量，异步 handler 执行后又把整个变量字典写回。
同一规则的 timer、startup 和消息事件可以并发运行。

**复现：** 两个事件各对计数器加一，预期为 2，最终持久化结果为 1。

**建议：** 对同一规则串行执行或引入事务式更新；不同规则可以受控并发。
明确取消、失败与状态提交的边界，防止修改状态后执行结果丢失。

### A11 / P2：一个耗时规则阻塞其他定时规则，后台任务缺少监督

**位置：** `tg_signer/automation/engine.py:198`、`:274`。

唯一 timer 循环逐个等待规则执行。长 delay、AI 调用或转发等待期间，
后面到期的规则无法执行。主流程等待 `idle()`，没有主动检查 timer 任务是否异常退出；
退出时取消后台任务也缺少 `try/finally` 和等待清理。

**复现：** 第一条到期规则等待事件，第二条已到期规则一直未运行；
释放第一条后第二条才运行。后台任务监督与清理问题由静态代码确认。

**建议：** 调度和执行分开，使用有限并发队列、规则锁、超时和重叠执行策略。
监督后台任务异常，并在关闭时等待取消完成。

### A12 / P2：配置和状态直接覆盖写入，写失败会破坏旧文件

**位置：** `tg_signer/automation/models.py:75`、`tg_signer/webui/data.py:129`、
`tg_signer/core.py:495`。

这些写入通过 `open(..., 'w')` 截断目标文件后进行序列化。
序列化失败、磁盘写入失败或写入时被其他进程读取，都会影响可恢复性。

**复现：** 状态文件原本有效；插件变量含不可序列化对象后，`save()` 抛出
`TypeError`，原文件被部分 JSON 覆盖，无法再次解析。

**建议：** 先完成序列化，再写同目录临时文件，完成必要的刷新后用
`os.replace` 原子替换。保留最近有效版本，并处理跨进程更新冲突。

### A13 / P2：任务名称能够跳出配置目录

**位置：** `tg_signer/webui/data.py:79`、`:129`；CLI 的任务目录拼接也需统一检查。

任务名称直接参与路径拼接，未限制目录分隔符、绝对路径或 `..`。

**复现：** 在临时工作区保存 `../../outside` 名称，生成的配置文件位于工作区外。

**影响与边界：** WebUI 操作要求已通过访问验证；这不是未登录读取漏洞。
但任务名能被误用为文件路径，保存或删除可能影响其他配置。

**建议：** 统一任务名称校验；解析后的目标必须位于预期任务目录内，
同时处理符号链接。高级工作目录设置应与任务名称保持独立。

### A14 / P2：外部转发忽略 HTTP 失败，部分 Telegram 调用绕过统一封装

**位置：** `tg_signer/core.py:1722`、`tg_signer/automation/handlers.py:394`、`:444`。

HTTP 回调没有检查响应状态，自动化调用后会增加成功计数。
`forward` 直接调用客户端，历史读取等路径也绕过工作器的统一调用封装。

**复现：** HTTP MockTransport 返回 503，回调仍正常返回，没有传播错误。
绕过统一调用封装由静态代码确认；未进行真实 FloodWait 压力验证。

**建议：** 检查 HTTP 状态与需要的业务返回值，记录明确的成功、失败和重试结果。
重用 HTTP 客户端。Telegram 调用继续集中到现有封装，保持统一限速和 FloodWait 策略。
重试发送或转发前应考虑重复提交风险。

## WebUI 与测试

### A15 / P2：公网访问验证还需要限速和权限边界

**位置：** `tg_signer/webui/app.py:282`、`:319`、`tg_signer/webui/views.py:632`。

访问码比较使用 `compare_digest`，但失败尝试没有限速或暂时锁定；
未设置访问码时允许直接进入。日志设置可指定服务进程能读取的任意文件路径。

**验证状态：** 静态审计确认；未对公网服务尝试暴力猜码。

**建议：** 公网部署增加登录失败限速、授权会话过期和 HTTPS，限制运行账户权限。
默认日志读取限定在允许的日志目录中。
保留当前默认监听本地地址的方式，对公网无访问码启动增加明确检查。
会话文件和本地 API 配置应显式使用私有文件权限。

### A16 / P2：CI 会跳过 WebUI 测试，运行边界测试不足

**位置：** `.github/workflows/test.yml:29`、`tests/test_webui_data.py:6`。

CI 安装普通项目依赖，未安装 `[gui]`；WebUI 测试使用
`pytest.importorskip('nicegui')`，因此标准 CI 环境会跳过这些测试。
当前测试较多覆盖单个函数，但不能拦住本次复现的跨模块运行问题。

**建议：** 保留基础 CLI 测试任务，另外添加安装 `[gui,yaml]` 的任务和浏览器测试。
优先补充回归场景：迁移失败恢复、RPC/动作超时、客户端启动失败、
共享客户端分发、配置生效、调度时钟、同规则并发和后台任务异常。
浏览器测试覆盖保存反馈、登录、工作区隔离和手机布局。

## 可选优化

1. **WebUI 使用数据库分页与聚合。** 目前页面刷新会分别读取完整记录给工作台和
   记录页，表格分页在客户端完成。可用 SQL 计算总数、14 天聚合、最近记录，
   按页查询记录并按需加载页面。当前规模没有做生产性能压测。
2. **明确关闭 SQLite 连接。** `with connection` 管理事务而不负责关闭连接。
   探针在关闭垃圾回收后执行 30 次读取，留下 30 个数据库文件句柄；
   垃圾回收后释放为 0。因此应避免依赖垃圾回收来释放连接。
   结合实际多进程写入需求再评估 WAL 与 busy timeout。
3. **补齐运行状态接口。** 展示实际运行进程、配置生效版本、下次计划、上次结果，
   然后通过明确的管理接口接入启动、停止、重载。进程控制需要单独的权限边界。
   自动化配置编辑作为后续能力，优先复用 automation 模型与校验。
4. **固定验证过的依赖范围、复用 AI 客户端。** GUI 等依赖范围较宽，部署没有完整
   依赖锁文件。建立可重复安装的部署约束并持续更新验证。
   `get_ai_tools()` 每次创建客户端，可按配置缓存并在关闭时释放资源。

## 建议实施顺序

1. 修复数据迁移删除顺序、执行结果判断、客户端启动失败、消息分发和 startup
   启动顺序，并增加回归测试。
2. 修复调度等待偏差，明确首次启动语义；让 WebUI 显示配置保存与生效状态。
3. 补齐配置校验、发送者过滤、原子写入和自动化并发调度。
4. 完善公网访问边界、WebUI CI 与数据库查询；再扩展运行控制和自动化编辑。

每一轮改动完成后再部署，验证真实账号时应保持已成功步骤的幂等性，
避免因服务重启或回归检查重复签到。
